# CI: 187 тестов, линт и сборка фронтенда на GitHub Actions

**Дата:** 2026-08-05
**Статус:** согласовано, план не написан
**Бэклог:** «Следующий шаг» в `docs/superpowers/specs/2026-08-05-split-bot-api-design.md`

## Зачем

В проекте нет ни CI, ни pre-commit. `ruff` настроен, но запускается руками; тесты гоняются
там же. Единственная автоматическая проверка перед боем — сборка образа, и она сообщает об
ошибке через 19 минут, уже во время деплоя.

Цель — чтобы каждый push в `main` и каждый PR проверялись без участия человека.
Проверяемый результат: коммит с падающим тестом или битым типом во фронтенде даёт красный
крест на GitHub.

## Что выяснила разведка

* Репозиторий **публичный** (`gh repo view` → `PUBLIC`), значит минуты Actions бесплатны и
  ограничения по времени можно не оптимизировать.
* `.github/` нет вообще — начинаем с нуля, ломать нечего.
* Продакшн-образ: `python:3.12-slim` и `node:22-alpine`. Локальная разработка идёт на
  Python 3.14 (`.venv/lib/python3.14`), `requires-python = ">=3.12"` допускает обе.
* `ruff format --check` уже проходит (`69 files already formatted`), включать можно сразу.
* `pytest` и `aiosqlite` объявлены в `[project.optional-dependencies].dev`, а не в
  `[dependency-groups]`, где лежит только `ruff`. Значит `uv sync --frozen` **без**
  `--extra dev` их не поставит.

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Платформа | GitHub Actions | Репозиторий уже на GitHub, публичный — бесплатно |
| Объём | Тесты с PostgreSQL + ruff + сборка фронтенда | Решение владельца. Сборка образа не входит |
| Структура | Один workflow, два параллельных job'а | Красный крест сразу показывает, что именно сломано; ~4 минуты вместо суммы |
| Триггеры | `push` в `main` и любой `pull_request` | Коммиты в этом проекте часто едут прямо в `main`; без push-триггера CI не запускался бы вовсе |
| Версия Python | 3.12, без matrix | Проверять надо то, что поедет в бой. Локальные 3.14 — осознанное расхождение |
| Path-фильтры | Нет | Required-проверка, которая не запустилась, висит «ожидает» вечно при branch protection |

## Архитектура

Один файл `.github/workflows/ci.yml`, два независимых job'а, `concurrency` с
`cancel-in-progress: true` — новый push отменяет незавершённый прогон предыдущего.

### Job `backend`

`ubuntu-latest`, Python 3.12, сервис-контейнер `postgres:17-alpine` с `POSTGRES_DB:
racetest` и healthcheck'ом (`pg_isready`).

Шаги по порядку:

1. `astral-sh/setup-uv` с включённым кешем.
2. `uv sync --frozen --extra dev` — **с `--extra dev`**, иначе не будет `pytest`.
3. `uv run ruff check core/ bot/ api/ tests/`
4. `uv run ruff format --check core/ bot/ api/ tests/`
5. `uv run pytest` с `TEST_DATABASE_URL`, указывающим на сервис-контейнер.
6. Страж пропусков (см. ниже).
7. Проверка миграций (см. ниже).

### Job `frontend`

`ubuntu-latest`, `actions/setup-node@v4` с Node 22 и кешем npm по
`webapp/package-lock.json`. Шаги: `npm ci`, затем `npm run build` — то есть
`tsc -b && vite build`.

## Две проверки сверх очевидного

Обе закрывают ловушки, уже задокументированные в `CLAUDE.md`, и обе важнее, чем сам факт
наличия CI.

### Страж пропусков

`tests/test_concurrency.py` молча пропускается без `TEST_DATABASE_URL`. Опечатки в
переменной достаточно, чтобы CI годами показывал зелёное на 182 тестах вместо 187 — а
пропущенные пять стерегут `_lock_item()` и `SELECT … FOR UPDATE`, то есть деньги.

Отдельный шаг гоняет этот файл и падает, если в выводе встречается `skipped`. Проверка на
слово, а не на «5 passed»: при добавлении шестого теста условие не устареет.

### Проверка миграций

Миграции PostgreSQL-only — `f1a2b3c4d5e6` использует `ctid` и `DELETE … USING`, и SQLite
их не видит никогда. Сегодня их не проверяет ничто, кроме деплоя.

Шаг применяет `alembic upgrade head` к сервис-контейнеру, затем запускает
`alembic revision --autogenerate` и падает, если сгенерированная миграция непустая.
Непустая означает, что модели и схема разъехались — ровно та поломка, которую в этом
проекте уже ловили руками после переименования пакета.

## Проверки самого CI

Мало написать workflow — надо доказать, что он ловит. В порядке возрастания доверия:

1. Прогон зелёный на текущем `main`.
2. **Красный на намеренно сломанном коде.** Временный коммит с падающим ассертом обязан
   дать красный крест. Без этой проверки нельзя отличить работающий CI от workflow,
   который тихо не запускается.
3. **Красный при отломанном `TEST_DATABASE_URL`.** Временно испортить переменную — страж
   пропусков обязан уронить job. Иначе он декоративный.
4. Лог содержит `187 passed`, а не `182 passed, 5 skipped`.

## Вне объёма

* Сборка Docker-образа в CI — решение владельца, не входит.
* Деплой из CI, публикация артефактов, coverage-пороги.
* Branch protection и required checks — это настройка GitHub, а не файл в репозитории;
  включается вручную владельцем.
* Pre-commit — следующая задача, отдельно.
* Matrix по версиям Python.

## Следующий шаг после этой работы

**Pre-commit.** Он ставится в каждом клоне отдельно и обходится флагом `--no-verify`,
поэтому ценность у него другая: не барьер, а ускоритель обратной связи — `ruff` за секунду
вместо четырёх минут ожидания CI. Настоящим барьером становится этот CI.
