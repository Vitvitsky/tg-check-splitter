# Разделение бота и API + выделение пакета `core`

**Дата:** 2026-08-05
**Статус:** согласовано, план не написан
**Бэклог:** пункт F1 в `docs/BACKLOG.md`

## Зачем

`entrypoint.sh` поднимает бота и uvicorn в одном контейнере и делает `wait -n`: падение
любого из двух процессов роняет контейнер целиком. Упал polling бота — перестал отвечать
и Mini App, хотя он ни при чём. Обратное тоже верно.

Цель — независимый рестарт и раздельные логи. Проверяемый результат: `docker compose kill
bot` не влияет на `/api/health`.

## Что выяснила разведка

Два факта изменили оценку задачи против того, что было записано в бэклоге.

**Связность бота и API почти нулевая.** Между процессами нет ни одного HTTP-вызова: оба
ходят прямо в Postgres. Уведомления API шлёт сырым HTTP в Telegram Bot API —
`api/services/notifications.py` помечен «no aiogram dependency». Бот не обращается к API.
Единственное, что их связывает, — `wait -n`.

**Пакет `bot/` — это на самом деле общее ядро.** `api/` импортирует из него 40 раз,
обратных импортов нет ни одного. Там лежат модели, БД, конфиг и сервисы, а не бот.

**Граница уже существует в коде.** Множество файлов, импортирующих `aiogram`, точно
совпадает с множеством бот-специфичных. Пересечения нет, резать по живому не придётся.

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Один образ или два | Один, три команды | Экономия от второго образа — единицы мегабайт (433 МБ это Python и зависимости), а `core/` нужен обоим |
| Кто гонит миграции | Отдельный одноразовый сервис `migrate` | Нет гонки по построению; падение миграции видно отдельно, а не тонет в логах приложения |
| Healthcheck бота | Нет, только `restart: unless-stopped` | Ловит падение процесса — это и есть цель. HTTP-сервер в боте вернул бы веб-часть, от которой его освобождаем |
| Переименовывать ли `bot/` → `core/` | Да | Решение владельца. Дороже минимального варианта на 40 файлов, но убирает ложь в именах |

## Архитектура

### Пакеты

```
core/                    новый; ноль зависимостей от aiogram
  config.py         37   настройки (12 импортов извне)
  db.py             52   движок и сессии
  utils.py          28   форматирование денег
  models/          205   base, session, payment, user_quota
  services/        932   session, quota, ocr, calculator

bot/                     остаётся; только aiogram
  __main__.py       31   polling
  handlers/        205   start, payment
  keyboards/        30
  i18n.py           25
  middlewares.py    18

api/                     не двигается; импортирует core/, не bot/
```

После этого `api` и `bot` — равноправные потребители `core`, не знающие друг о друге.

### Контейнеры

Три сервиса из одного образа, различаются только командой.

```yaml
services:
  migrate:
    build: .
    command: ["uv", "run", "alembic", "upgrade", "head"]
    restart: "no"
    depends_on: { db: { condition: service_healthy } }

  api:
    build: .
    command: ["uv", "run", "uvicorn", "api.app:create_app",
              "--factory", "--host", "0.0.0.0", "--port", "8005"]
    ports: ["8005:8005"]
    healthcheck:
      # curl в python:3.12-slim НЕТ — проверено. Проба через stdlib urllib.
      test: ["CMD", "python", "-c",
             "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8005/api/health').read()"]
    restart: unless-stopped
    depends_on: { migrate: { condition: service_completed_successfully } }

  bot:
    build: .
    command: ["uv", "run", "python", "-m", "bot"]
    restart: unless-stopped
    depends_on: { migrate: { condition: service_completed_successfully } }
```

`api` и `bot` зависят от `migrate`, но **не друг от друга**.

`entrypoint.sh` удаляется целиком: миграции ушли в `migrate`, `wait -n` — ровно та
конструкция, от которой избавляемся, а `CMD` в `Dockerfile` не нужен, раз каждый сервис
задаёт `command`.

Порядок старта по смыслу не меняется: сегодня `alembic upgrade head` тоже гоняется при
каждом запуске контейнера.

Здесь у `api` появляется healthcheck, которого сейчас нет ни у одного сервиса приложения.

## Что ломается и требует правки

**Имя контейнера.** `tg-check-splitter-app-1` исчезает; появляются `-api-1`, `-bot-1`,
`-migrate-1`. Рецепты отладки в `CLAUDE.md`, записанные 2026-08-04, ссылаются на старое
имя и перестанут работать:

```bash
docker logs tg-check-splitter-app-1 | grep -E 'POST .../(vote|tip)'   # больше нет
```

Обновление `CLAUDE.md` и `README.md` — часть работы, отдельным шагом плана. Взамен
появляются раздельные `docker compose logs bot` и `logs api`, которых сегодня нет.

**Три места, которые не ловятся автоматически:**

* `alembic/env.py:9-10` — `from bot.config`, `from bot.models`. Если забыть,
  автогенерация увидит пустую схему и предложит удалить все таблицы.
* `Dockerfile` — рядом с `COPY bot/ bot/` нужен `COPY core/ core/`.
* `pyproject.toml` — трогать **не** надо: пакет не устанавливается
  (`uv sync --no-install-project`), модули берутся из рабочей директории. Проверено.

## Порядок работы

Два коммита, не один:

1. Переименование `bot/` → `core/` через `git mv` (сохраняет историю файлов — это те
   файлы, где живут блокировки и расчёт денег), правка импортов в 40 файлах, зелёные
   тесты.
2. Разделение на три сервиса.

Первый коммит самодостаточен и разворачивается отдельно: `entrypoint.sh` продолжает
работать, потому что `python -m bot` остаётся валидным — пакет `bot` никуда не делся,
из него лишь вынули общее ядро. То есть переименование можно выкатить и убедиться, что
бой жив, до того как трогать топологию.

При откате топологии переименование остаётся.

## Проверки

В порядке возрастания доверия.

1. **`ruff check`** — уронит сборку на любом осиротевшем импорте. Бесплатный первый
   фильтр.
2. **226 тестов** — `uv run pytest`.
3. **Тесты конкурентности с настоящим PostgreSQL.** `tests/test_concurrency.py` молча
   пропускается без `TEST_DATABASE_URL` (известная ловушка, описана в `CLAUDE.md`), а
   переезжает ровно тот код, который они стерегут: `_lock_item()` и `SELECT … FOR UPDATE`
   в `services/session.py`. Прогон без реальной БД показал бы зелёный экран, ничего не
   проверив. Шаг плана обязан **подтвердить, что эти тесты исполнились**, а не
   пропустились.
4. **Изоляция окружения:** `FREE_SCANS_PER_MONTH=99 uv run pytest` должен пройти.
5. **Alembic видит модели:**

   ```bash
   uv run alembic revision --autogenerate -m "should-be-empty"
   ```

   Миграция обязана получиться пустой. Непустая означает, что `target_metadata` потеряла
   модели. Файл после проверки удаляется.

6. **Приёмка разделения** — то, ради чего всё делается:

   ```bash
   docker compose kill bot
   curl -fsS http://127.0.0.1:8005/api/health     # обязан отвечать
   docker compose ps bot                          # обязан подняться сам
   ```

   Сегодня первая команда убила бы и API. Симметрично: `kill api` не должен ронять бота.

## Вне объёма

* `api/` не трогается, кроме строк импорта.
* Фронтенд не трогается.
* `api/services/notifications.py` не переезжает в `core/` — им пользуется только API,
  переезд ради симметрии добавил бы работы без выигрыша.
* Боту не добавляется healthcheck.
* `bot/keyboards/` не удаляется: вопреки подозрению, он живой — `handlers/start.py:19`.
* Пункт A бэклога (несколько воркеров + Redis) не затрагивается. `ConnectionManager` в
  `api/ws.py` остаётся процессно-локальным; разделение безопасно, пока API — один
  процесс. Масштабировать API можно будет только после пункта A.

## Следующий шаг после этой работы

**Pre-commit и CI.** В проекте нет ни того, ни другого: `ruff` настроен, но запускается
только руками. Pre-commit дёшев и полезен, однако это отдельная задача — к разделению
сервисов он отношения не имеет, и смешивать их в одном плане не стоит.

Стоит учесть, что без CI pre-commit остаётся единственным автоматическим барьером, а он
ставится в каждом клоне отдельно и обходится флагом `--no-verify`. То есть настоящий
пробел здесь — CI, который гонял бы 226 тестов на push; pre-commit лишь ловит опечатки
раньше. Разумный порядок: сначала CI, затем pre-commit как ускоритель обратной связи.
