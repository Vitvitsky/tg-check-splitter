# Бэклог

Что осознанно не сделано и при каких условиях за это стоит браться. Каждый пункт —
с триггером: признак, по которому видно, что момент настал. До триггера работа не

Все числа ниже — замеры на текущем хосте (4 ядра, 7.4 ГБ RAM, 18 ГБ свободного диска),

## A. Несколько воркеров API + Redis pub/sub

**Статус:** не начато. Единственное, что мешает горизонтальному масштабированию.

### В чём проблема

`ConnectionManager` в `api/ws.py` держит WebSocket-соединения в словаре внутри процесса:

```python
self._connections: dict[str, set[WebSocket]] = {}
```

`broadcast()` доходит только до клиентов, подключённых к **этому** воркеру. Запустите
второй — и участник, чей WebSocket попал на воркер A, не увидит голоса участника с
воркера B. Приложение не упадёт, просто интерфейс перестанет обновляться вживую у
части людей. Это худший вид поломки: тихий и воспроизводимый через раз.

Раньше воркер был один ещё и из-за фото в памяти процесса — это уже исправлено
(миграция `a7c3e91b40d2`), осталось только WebSocket.

### Что делать

Заменить внутренний словарь на Redis pub/sub: каждый воркер подписывается на канал
`session:{id}`, `broadcast()` публикует в канал вместо прямой рассылки, а локальный
словарь остаётся только для доставки своим подключённым клиентам.

Объём работы небольшой — меняется один класс `ConnectionManager` и добавляется
контейнер. Тесты в `tests/test_api/test_ws.py` придётся дополнить проверкой, что
событие, опубликованное «другим воркером», доходит до клиента.

### Требования к ресурсам

Замеры сейчас:

| | Значение |
|---|---|
| Память контейнера `app` (бот + API) | 200 МБ |
| Память Postgres | 58 МБ |
| Свободно RAM на хосте | ~2.0 ГБ |
| Ядер | 4 |
| Пропускная способность одного воркера | ~110 req/s на эндпоинтах с БД |
| Соединений к Postgres используется | 7 из 100 |

Что добавится:

- **Redis:** `redis:7-alpine`, только pub/sub, персистентность не нужна
  (`--save "" --appendonly no`). Реальный расход — 10–15 МБ RSS; `maxmemory 64mb`
  берётся с большим запасом. Публикуемые события крошечные (десятки байт), очередей
  не копится, потому что подписчики читают сразу.
- **Воркеры:** каждый добавляет ~150–200 МБ RAM и свой пул соединений к БД.

**Ограничение, которое считать обязательно** — пул соединений. Сейчас
`DB_POOL_SIZE=20` плюс `DB_MAX_OVERFLOW=10` = до 30 соединений **на воркер**. При
`max_connections=100` у Postgres:

| Воркеров | Соединений максимум | Вердикт |
|---|---|---|
| 1 | 30 | сейчас |
| 2 | 60 | нормально |
| 3 | 90 | впритык, не останется места для миграций и psql |
| 4 | 120 | **превышает лимит**, часть запросов упрётся в `FATAL: too many connections` |

То есть при переходе на 3+ воркера **обязательно** снижать `DB_POOL_SIZE` пропорционально
(например 12 при трёх воркерах) или поднимать `max_connections` у Postgres, что стоит
памяти на стороне БД. Помните, что соединение здесь дорогое (~80 мс на установку,
см. `core/db.py`), поэтому резать пул слишком сильно тоже нельзя.

Реалистичный потолок на этом хосте: **2–3 воркера, ~250–330 req/s**, около 600 МБ RAM
на приложение плюс 15 МБ на Redis. Упрётся всё это скорее в 4 ядра, чем в память.

Бот запускать во втором экземпляре **нельзя** — long polling в двух процессах приведёт
к дублированию обработки апдейтов. Отдельным сервисом compose он уже вынесен (F1);
масштабировать надо только `api`, `bot` остаётся ровно в одном экземпляре.

### Триггер

Не раньше, чем один воркер начнёт стабильно упираться. Признаки: p95 на
`/api/sessions/my` уходит за 1 с при обычной нагрузке, или `docker stats` показывает
устойчивую загрузку CPU контейнера выше ~70%. Сейчас — 0.27%.

При нынешней нагрузке (десяток человек за столом) 110 req/s избыточны примерно
стократно.

## B. Таблица `user_activity` для точных DAU/MAU

**Статус:** не начато. `tools/stats.sh` считает метрики уже сейчас, но с оговоркой.

### Как смотреть статистику сегодня

```bash
./tools/stats.sh mau        # DAU / WAU / MAU и липкость
./tools/stats.sh dau 30     # активные по дням
./tools/stats.sh funnel     # воронка: сессия -> фото -> распознано -> голоса -> расчёт
./tools/stats.sh retention  # возврат по месячным когортам
./tools/stats.sh money      # платежи и упирающиеся в лимит
./tools/stats.sh health     # размеры таблиц, объём неочищенных фото
./tools/stats.sh all
```

Активность собирается объединением четырёх таблиц, где уже есть `user_tg_id` и время:
`sessions`, `session_members`, `item_votes`, `payments`. Считается фактическое
действие, а не открытие приложения.

### Почему этого со временем перестанет хватать

Две причины, и первая серьёзнее:

1. **Данные за прошлое стираются.** `DELETE /api/sessions/history` удаляет
   рассчитанные сессии, а каскад уносит участников и голоса. Вместе с ними исчезает
   свидетельство активности: DAU за прошлый вторник сегодня может оказаться меньше,
   чем был вчера. Цифры не воспроизводятся задним числом.
2. **Не видно тех, кто просто заходил.** Открыл приложение, посмотрел итог, ушёл —
   в метрику не попал. Для DAU это отчасти правильно, но занижает охват.

### Что делать

Таблица на два столбца, по строке на пользователя в день:

```sql
CREATE TABLE user_activity (
    user_tg_id BIGINT NOT NULL,
    day        DATE   NOT NULL,
    PRIMARY KEY (user_tg_id, day)
);
```

Запись — из middleware на каждый авторизованный запрос, одним оператором:

```sql
INSERT INTO user_activity (user_tg_id, day) VALUES ($1, CURRENT_DATE)
ON CONFLICT DO NOTHING;
```

Идемпотентно, не более одной новой строки на человека в день, к сессиям не привязано и
потому переживает удаление истории. Объём: при 1000 активных пользователей в месяц —
около 30 тысяч строк в месяц, порядка 2 МБ в год.

### Отдельный воркер для этого не нужен

Ни cron, ни фоновая задача не требуются, и вот почему:

- запись — один дешёвый upsert внутри уже идущего запроса;
- чтение — агрегат по таблице с индексом; на сотнях тысяч строк это миллисекунды.

Воркер оправдан только если понадобятся **суточные снимки** метрик (чтобы сравнивать
«что показывала панель месяц назад») или тяжёлые когортные отчёты. Это уже отдельный
продукт, и до него далеко.

### Триггер

Как только цифры начнут кому-то показывать или на них опираться в решениях. Пока
статистику смотрит один человек глазами — хватает `tools/stats.sh`.

## C. Мелочи, руки не дошли

- **Уведомления шлются последовательно**, и на каждое сообщение создаётся новый
  `httpx.AsyncClient` — то есть новое TCP+TLS рукопожатие. При десяти участниках это
  десять рукопожатий подряд. Плюс у Telegram лимит ~30 сообщений в секунду и нет
  обработки `429`. Лечится общим клиентом и `asyncio.gather` с ограничением
  параллельности.
- **Дробное деление блюда невозможно.** `split_remaining_equally()` раздаёт целые
  порции, поэтому одно нераспределённое блюдо на троих достаётся одному целиком.
  Арифметика при этом верна — итог всегда равен чеку. Честное деление потребует
  сделать `ItemVote.quantity` дробным, а это изменение схемы и правка интерфейса.
- **CORS разрешает `http://localhost:5173`** и в проде (`api/app.py`). Безвредно, пока
  никто не открывает Mini App с локального фронтенда, но в проде этому не место.
- **Content-type загружаемых фото не проверяется** — ограничен только размер. Не-картинка
  просто уедет в LLM и вернётся ошибкой разбора, за которую скан теперь возвращается.

## D. Режим «поделить поровну на всех»

**Статус:** идея. Самое дешёвое из непостроенного и, вероятно, самое востребованное.

### Зачем

Сейчас единственный способ разделить счёт — каждый отмечает свои блюда. Часто это
лишняя работа: компания просто хочет разделить итог поровну и разойтись. Воронка
показывает, что до голосования доходит половина сессий, а до расчёта — ни одна;
возможно, дело именно в том, что путь слишком длинный для типичного случая.

### Что делать

Кнопка на экране позиций: «Поделить поровну» — и сразу расчёт, минуя голосование.

Развилка в реализации, и она важнее, чем кажется:

- **Делить сумму.** `total / n`, остаток в копейках — первым по списку. Точно, просто,
  но обходит `calculate_shares()`, который выводит доли из голосов. Значит появляется
  второй путь расчёта, и всё, что построено вокруг первого (заморозка после расчёта,
  идемпотентность, `/shares`, `/my-share`), нужно проверить на нём отдельно.
- **Раздать голоса.** Проставить каждому участнику долю каждой позиции и посчитать как
  обычно. Один путь расчёта, всё существующее работает без изменений — но упирается в
  целочисленность `ItemVote.quantity`: блюдо в одном экземпляре на троих не делится,
  ровно та же проблема, что в пункте C.

Рекомендую делить сумму, но не как отдельный режим, а как **предзаполнение**: раздать
доли и позволить дальше править их вручную. Тогда «поровну» — это стартовая точка
голосования, а не параллельная ветка расчёта. Дробные доли всё равно понадобятся.

Чаевые остаются персональными: делится счёт, а не желание оставить на чай.

### Триггер

Как только появится хоть одна компания, реально дошедшая до расчёта, — спросить, чего
им не хватило. Сейчас таких данных нет, и выбирать развилку не на чем.

## E. Игровые механики: случайный набор и лотерея

**Статус:** идея. Требует решений, которых пока нет ни у кода, ни у продукта.

### Что хочется

- **Случайный набор блюд** — вместо выбора вручную участникам раздаются позиции
  жребием.
- **Лотерейный билет** — один вытянутый участник платит за всех.
- Играть можно только если **все участники вошли** и согласились.

### Что здесь нетривиально

**1. Честность должна быть доказуемой, а не заявленной.** Лотерея решает, кто заплатит
три тысячи. `random.choice()` на сервере проверить нельзя: проигравший не отличит
случайность от того, что админ подкрутил. Схема commit-reveal решает это дёшево —
сервер публикует хеш «зерно + соль» до розыгрыша и раскрывает зерно после, любой
пересчитывает и убеждается. Без этого механика работает ровно до первого спора.

**2. Согласие, а не присутствие.** «Все залогинились» — правильный инстинкт, но
недостаточный: человек присоединился делить счёт, а не рисковать полной суммой.
Согласие должно быть явным и от каждого, отдельно от `confirmed` (который сейчас
означает «я выбрал блюда и чаевые», а в лотерее выбирать нечего). Значит нужен либо
новый флаг готовности, либо игра запускается вместо голосования, а не после.

**3. Результат обязан попасть под заморозку.** Расчёт теперь идемпотентен и
неизменяем; розыгрыш должен разыгрываться **один раз** и становиться частью этого
слепка. Примитив уже есть — условный `UPDATE`, как в `claim_settlement()`. Перерозыгрыш
после того, как людям ушли пуши, недопустим.

**4. Как это ложится на модель расчёта.** Дешевле всего не добавлять режим, а раздать
голоса: победителю лотереи — все позиции целиком, остальным ничего. Тогда
`calculate_shares()`, заморозка, `/shares` и уведомления работают без единой правки.
Случайный набор блюд ложится туда же — это просто другой способ расставить голоса.

**5. Случайность и тесты.** Весь код детерминирован и проверяется прогонами; источник
случайности придётся внедрять параметром, иначе тесты станут плавающими.

### Чем начать

Случайный набор блюд, не лотерея. Ставки нулевые — итог всё равно равен чеку, никто не
рискует чужой суммой, доказуемая честность не нужна. Это позволяет проверить, заходит
ли игровая механика вообще, не строя commit-reveal и не разбираясь с согласием.

### Триггер

После пункта D. Пока типовой сценарий «поделить поровну» требует ручного выбора блюд,
развлечения преждевременны.

## F. Разделить бота и API; отдельно — переписать бэкенд на Rust

**Статус:** F1 сделано 2026-08-05, F2 не начато. Предложение пришло целиком, но внутри
него две разные задачи с очень разной ценой, и их стоит развести.

### Целевая схема из предложения уже почти построена

Предлагалось: бот отдельно, Mini App отдельно, общий API, Postgres, Docker Compose,
HTTPS через reverse proxy с Let's Encrypt. Всё это, кроме языка, здесь уже есть:

| Компонент | В предложении | Сейчас |
|---|---|---|
| Bot | Rust + teloxide | Python + aiogram, polling, `bot/handlers/` — 205 строк |
| API | Rust backend | FastAPI, `api/` |
| DB | Postgres | Postgres 17, отдельный контейнер |
| Frontend | static за Nginx | Vite-сборка, вшита в образ, отдаёт её же API |
| Deploy | Docker Compose | Docker Compose |
| HTTPS | Nginx/Caddy + LE | Nginx + certbot, `nginx/tg-check-splitter.conf` |

Реальная разница осталась ровно в одном — языке. Бот и API жили **одним контейнером**
(`entrypoint.sh` поднимал оба процесса и делал `wait -n`); с 2026-08-05 это три
отдельных сервиса, см. F1.

### F1. Разделить бота и API на два сервиса

Дёшево и полезно само по себе. До 2026-08-05 `wait -n` означал, что падение любого из
двух процессов роняет контейнер целиком: упал polling бота — перестал отвечать и Mini App,
хотя он ни при чём. Обратное тоже верно. Отдельные сервисы дают независимый рестарт,
раздельные логи и раздельные healthcheck'и.

Что мешает: `ConnectionManager` в `api/ws.py` держит WebSocket-соединения в памяти
процесса — то же самое ограничение, что и в пункте A. Пока API один процесс, разделение
безопасно; если разделять и одновременно масштабировать API, сначала нужен пункт A.

**Сделано 2026-08-05.** См. `docs/superpowers/plans/2026-08-05-split-bot-api.md`.

### F2. Переписать бэкенд на Rust

Триггера нет, и замеры против. Аргумент за Rust — производительность и память; ни того,
ни другого сейчас не не хватает (замеры на текущем хосте):

```
tg-check-splitter-app-1   CPU 0.19%   RSS 198.8 MiB
tg-check-splitter-db-1    CPU 0.00%   RSS  54.1 MiB
доступно на хосте                     4081 MiB
```

Узкое место, которое здесь действительно измеряли, — не язык, а пул соединений к
Postgres: открытие соединения ~80 мс против ~0.19 мс на запрос, и `pool_size=20` поднял
`/api/quota` с 22–32 до 105–130 req/s (см. CLAUDE.md). Rust этот эффект не отменяет.

Цена переписывания: 3196 строк Python, из них самое неприятное — не бизнес-логика, а
то, что придётся воспроизводить заново:

* Stars-платежи (`bot/handlers/payment.py`) — единственное, что зарабатывает;
* i18n на Babel (`locales/`, `babel.cfg`);
* Alembic-миграции, включая PostgreSQL-специфичные (`ctid`, `DELETE … USING`);
* блокировки в `core/services/session.py` и тесты конкурентности к ним — именно они
  держат корректность денег.

Отдельно стоит заметить, чего Rust **не** чинит. Все пять багов, разобранных 2026-08-04
(«Confirm Selection ничего не делает», голоса не сохранялись, вторая порция не бралась,
цикл автосохранения чаевых), — фронтендовые: невызванный `init()` Telegram SDK,
невызванный `restoreInitData()`, нестабильная ссылка в зависимостях `useEffect`. Ни один
из них не связан с языком бэкенда и после переписывания остался бы на месте.

**Триггер:** CPU API устойчиво выше ~70% на одном ядре под реальной нагрузкой, либо RSS
за 1 ГБ, либо потребность в задержках, недостижимых на asyncio. До этого переписывание
меняет рабочий код на нерабочий без выигрыша.

Если Rust хочется как самоцель — дешёвый способ попробовать, ничем не рискуя: вынести на
нём один изолированный сервис без денег и без состояния. Кандидат — OCR-прокси к Z.AI
(`core/services/ocr.py`, 258 строк), у него узкий контракт и уже есть возврат кванты при
сбое.
